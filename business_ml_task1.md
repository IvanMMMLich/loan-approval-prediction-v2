## В чём задание

Нужно было привести учебный ML-проект (предсказание одобрения кредита) к production-стандартам. Задание состоит из трёх пунктов: отрефакторить код под production-стандарты, настроить Poetry, pre-commit и линтер, интегрировать виртуальное окружение в Git-репозиторий.

Общая идея одной фразой: любой человек клонирует репозиторий, выполняет `poetry install` и получает рабочий проект с тем же окружением, а некачественный код не может попасть в коммит.

Важное условие задания: ML-логика не менялась. Шаги 1–7, модель, гиперпараметры и метрики остались прежними — менялось только оформление кода и способ установки зависимостей. Контроль этого условия: метрика ROC-AUC до и после рефакторинга (раздел «Сравнение ROC-AUC»).

## Словарь

- **Poetry** — менеджер зависимостей Python. Как «умный список покупок»: вместо того чтобы вручную ставить десятки пакетов нужных версий, вы описываете список один раз, а Poetry сам ставит всё нужное и не ставит лишнего.
- **Линтер** — программа, которая проверяет код на стилистические ошибки и подозрительные места: неиспользуемые импорты, неотсортированные блоки, опасные конструкции. Как «корректор текста»: текст тот же, но читать его проще, а ошибок меньше.
- **Pre-commit** — система автопроверок перед коммитом. Как «швейцар на входе»: не прошёл проверку — коммит не попадёт в историю. Каждый коммит автоматически проверяется теми же правилами, что и весь проект.
- **Lock-файл** — файл с точными версиями всех пакетов и их зависимостей. Как «чек из магазина с артикулами»: в списке покупок написано «молоко», а в чеке — конкретная марка и упаковка. Два человека с одним lock-файлом получат одинаковое окружение.
- **Виртуальное окружение** — изолированная «комната» под проект, где стоят только его зависимости и ничего не конфликтует с другими проектами и системой. Poetry создаёт такую комнату сам по описанию из файла проекта.

## Разбор метрик

**1. Строк в файле зависимостей.** Что значит: сколько строк занимает описание зависимостей. Что показала: было 39 строк в `requirements.txt` (40 записей), стало 15 записей в `pyproject.toml` (12 основных + 3 dev) плюс строка ограничения Python. Как интерпретируем: файл стал в два с лишним раза короче, потому что в нём остались только прямые зависимости, а не весь снимок окружения.

**2. Прямых зависимостей.** Что значит: сколько записей в файле зависимостей действительно импортируется в коде проекта. Что показала: было 13 прямых из 40 (плюс 25 транзитивных, 1 неиспользуемый и 1 дубль), стало 15 прямых из 15. Как интерпретируем: раньше файл был свалкой всего установленного окружения; теперь каждая запись оправдана, а транзитивные зависимости подтягиваются автоматически и фиксируются в lock-файле. Примечание о предварительном осмотре: до точного замера оценка была «12 прямых / 23 транзитивных / 3 мусорных» — пакеты plotly и graphviz изначально считались неиспользуемыми, но проверка фактических зависимостей (`pip show <пакет> | grep Required-by`) показала, что их требует CatBoost, то есть это транзитивные зависимости, а не мусор. Точные цифры зафиксированы в before.txt: 13 прямых (12 основных + pytest), 25 транзитивных, 1 неиспользуемый (imbalanced-learn), 1 дубль (pytest).

**3. Конфликтов и дублей версий.** Что значит: сколько пакетов указано в файле более одного раза с разными версиями. Что показала: был один дубль — pytest 7.4.0 и 9.0.3 (pip молча брал последнюю), стало ноль. Как интерпретируем: Poetry не допускает такой ситуации — резолвер сам решает конфликты и падает с понятной ошибкой, если версии несовместимы.

**16. Способ установки зависимостей CI.** Что значит: откуда облачная проверка берёт версии пакетов. Что показала: раньше — ручной список из шести пакетов без версий, игнорирующий файл зависимостей; теперь — `poetry install` из lock-файла. Как интерпретируем: CI проверяет код в том же окружении, в котором код реально работает, а не в случайном «последнем на момент запуска».

**17. Команд для развёртывания с нуля.** Что значит: сколько действий нужно новому человеку, чтобы получить рабочее окружение. Что показала: было 3 (`python -m venv`, `source activate`, `pip install -r requirements.txt`), стало 2 (установка Poetry один раз, затем `poetry install`). Как интерпретируем: меньше шагов — меньше мест, где можно ошибиться; плюс исчезла разница между «что написано в файле» и «что фактически установлено».

## Отклонения от ТЗ

Все отклонения осознанные, с причинами:

1. **Python: `>=3.11,<3.14` вместо `>=3.11,<3.13`; Docker и CI переведены на 3.13 вместо 3.11.** На ноутбуке автора установлен только Python 3.13.2, поэтому локальная работа с ограничением `<3.13` была бы невозможна. Чтобы версия была одна везде, Docker и CI тоже переведены на 3.13 (по решению автора).
2. **xgboost: 1.7.6 → 2.1.4.** У xgboost 1.7.6 нет колёс для Python 3.13 (в старом окружении он стоял из cp38-колеса, что невозможно в чистом окружении). Взят ближайший совместимый выпуск; API `XGBClassifier` не изменился, на сравнение ROC-AUC не влияет (xgboost используется только в скрипте сравнения моделей, не в финальном пайплайне).
3. **Точные пины вместо caret-диапазонов.** ML-стек (numpy, pandas, scipy, scikit-learn, lightgbm, а также остальные прямые зависимости) закреплён точными версиями, фактически стоявшими в окружении «до» (сняты через `pip freeze` на шаге 0). Цель — гарантировать, что ROC-AUC «до» и «после» считается на одном и том же стеке моделирования. Не-точные ограничения использованы только там, где бамп неизбежен: xgboost — диапазон `>=2.1.4,<3.0.0`, pre-commit — caret `^4.0.0`.
4. **`.dockerignore` добавлен сверх списка ТЗ.** Без него сборка Docker потащила бы в контекст папки `.venv-legacy` (918 МБ по `du -sh`) и `.git`; файл состоит из 13 строк и защищает сборку от мусора. Добавлен по согласованию с автором.
5. **README: правки минимальны и только по ТЗ.** Старый раздел «Как запустить» (инструкции через pip) оставлен без изменений как исторический — по условию задания README можно только дополнять. Актуальный способ установки описан в новом разделе «Установка через Poetry».
6. **Метрика 1 «после»:** файла `requirements.txt` больше нет, поэтому сравниваются «записи зависимостей»: 40 записей старого файла против 15 записей двух секций `pyproject.toml` (+ строка `requires-python`). Определение зафиксировано в файлах замеров.
7. **`strict=False` в `zip()`:** добавлен явно в 16 местах по правилу B905. Выбран `False`, а не `True`, чтобы сохранить прежнее поведение кода один в один.
8. **Dockerfile пришлось доработать по результатам реальной сборки и запуска контейнера.** Два дефекта всплыли только при фактической проверке: (а) Poetry не мог установить проект, потому что README.md ещё не был скопирован в образ, — добавлен `COPY README.md`; (б) LightGBM не запускался в контейнере из-за отсутствия `libgomp1` (библиотека OpenMP) — добавлена установка через apt. Показательно, что старый Dockerfile страдал той же проблемой: его образ тоже не запустил бы пайплайн. Итог проверки: образ собирается, пайплайн внутри контейнера выдаёт тот же ROC-AUC = 0.9587 ± 0.0033.

## Как проверить

1. Клонировать репозиторий и установить окружение:
   ```bash
   curl -sSL https://install.python-poetry.org | python3 -
   poetry install
   ```
2. Убедиться, что код чистый:
   ```bash
   poetry run pre-commit run --all-files
   ```
3. Прогнать тесты:
   ```bash
   poetry run pytest tests/ -v
   ```
4. Контроль ML-поведения (несколько минут):
   ```bash
   poetry run python src/step7_pipeline/pipeline_cv.py
   ```
   ROC-AUC должен быть 0.9587 ± 0.0033 (значение из замеров «до» и «после»).
5. Сборка и запуск в Docker (проверено в ходе работы: образ собирается и
   пайплайн запускается внутри контейнера):
   ```bash
   docker build -t loan-approval-prediction .
   docker run loan-approval-prediction
   ```

Сырые замеры: `docs/task1_metrics/before.txt` (до) и `docs/task1_metrics/after.txt` (после).
