# Процесс автоматического переобучения модели

Схема в нотации BPMN, передана через Mermaid `flowchart` (GitHub отрисовывает её
прямо на странице). Условные обозначения: круги — события, прямоугольники — задачи,
ромбы — развилки, подграфы — участники процесса.

Схема построена на компонентах, которые уже есть в проекте: пайплайн обучения
(`src/step7_pipeline/`), MLflow (метрики и реестр версий), Docker, CI. В описании
каждого этапа честно отмечено, что уже реализовано, а что описано как целевой процесс.

## Схема

```mermaid
flowchart TD
    subgraph Сбор данных
        T((Триггер переобучения))
        D1[Получить новую порцию данных]
        D2[Подготовить признаки, как в пайплайне]
    end

    subgraph Обучение
        TR[Обучить новую версию модели]
    end

    subgraph Проверка качества
        EV[Оценить ROC-AUC на кросс-валидации]
        G{ROC-AUC новой >= текущей?}
    end

    subgraph Регистрация и деплой
        REG[Зарегистрировать новую версию в MLflow]
        DEP[Переключить алиас champion на новую версию]
        DONE((Версия в эксплуатации))
        REJ((Отклонено: версия не публикуется))
    end

    T --> D1
    D1 --> D2
    D2 --> TR
    TR --> EV
    EV --> G
    G -- да --> REG
    G -- нет --> REJ
    REG --> DEP
    DEP --> DONE
```

## Описание этапов

**1. Триггер запуска переобучения (событие).** Запускает цикл. Триггерами могут быть:
появление новой порции данных, ухудшение метрик на свежих данных (дрейф) или запуск по
расписанию. В текущем проекте автоматического триггера нет — это целевой процесс;
сейчас переобучение запускается вручную.

**2. Получение и подготовка новых данных (задачи).** Берётся новая порция заявок и
приводится к тем же 9 признакам, что и в обучении (`person_income` через Box-Cox,
категориальные через Ordinal Encoding). Подготовка признаков реализована внутри
sklearn `Pipeline` (`src/step7_pipeline/pipeline_cv.py`).

**3. Обучение новой версии (задача).** На новых данных обучается новая версия той же
модели LightGBM с теми же гиперпараметрами. Этот этап реализован: `create_pipeline()` +
`run_cross_validation()` в `src/step7_pipeline/pipeline_cv.py`.

**4. Проверка качества (задача + развилка).** Новая версия оценивается на 5-Fold
кросс-валидации по ROC-AUC. Реализовано: `run_cross_validation()` считает ROC-AUC,
accuracy, precision, recall, f1 по фолдам и среднее.

**5. Решение о возможности публикации (развилка).** Сравнивается ROC-AUC новой версии
с ROC-AUC текущей версии в эксплуатации (алиас `champion` в MLflow). Если новая версия
не хуже — публикуем; если хуже — отклоняем. Автоматическое сравнение в коде не реализовано,
описано как целевой процесс; на защите сравнение выполняется вручную по метрикам в MLflow.

**6. Регистрация новой версии (задача).** Новая версия регистрируется в MLflow Model
Registry через `mlflow.sklearn.log_model` + `register_model`. Этот этап реализован в
`src/monitoring/log_final_model.py` (логирование модели и версии).

**7. Деплой (задача).** Алиас `champion` переключается на новую версию, после чего именно
она считается рабочей. В MLflow реализована смена алиаса; автоматический деплой в продакшн
(например, через Docker-образ с новой моделью) — целевой процесс, описан, но не автоматизирован.

**8. Действия при неуспешном прохождении проверок (событие).** Если новая версия хуже —
она не публикуется; в MLflow остаётся запись о запуске с метриками, по которым видно,
почему версия отклонена, а в эксплуатации остаётся прежняя версия `champion`. Дальше
разбираются причины ухудшения (данные, дрейф, ошибки подготовки).

## Что реализовано, а что описано как целевой процесс

- **Реализовано сейчас:** подготовка признаков и обучение (step7 Pipeline), оценка
  ROC-AUC кросс-валидацией, регистрация метрик и артефактов в MLflow, регистрация модели
  в Registry с алиасом `champion`, проверки CI (ruff, pytest) и сборка Docker.
- **Целевой процесс (описано, автоматизации нет):** автоматический триггер по расписанию
  или дрейфу, автоматическое сравнение новой версии с текущей и авто-переключение алиаса,
  автоматический деплой новой версии.

## Как посмотреть результат в MLflow

1. Запустить UI локально:
   ```bash
   poetry run mlflow ui
   ```
2. Открыть в браузере: http://127.0.0.1:5000
